# 基于深度学习的睡眠状态事件检测实验报告

## 一、项目背景

本项目来自 Kaggle 比赛 **Child Mind Institute - Detect Sleep States**。该任务的目标是根据手环传感器采集到的时间序列数据，自动检测儿童睡眠过程中的两个关键事件：

- `onset`：入睡时刻
- `wakeup`：醒来时刻

数据主要包括每个时间步的传感器特征，例如：

- `anglez`：手腕角度
- `enmo`：运动强度
- `timestamp`：时间戳
- `series_id`：每个受试者或记录序列的编号
- `step`：时间序列中的步数

本质上，这是一个 **时间序列事件检测问题**。与普通分类任务不同，模型不仅要判断“是否睡觉”，还要准确定位事件发生的时间点。因此，最终评价不仅关注分类是否正确，还关注预测事件与真实事件之间的时间距离。

本项目的主要目标不是单纯追求排行榜最高分，而是完整体验一个 AI 项目的流程，包括数据理解、特征构造、模型训练、调参、后处理、提交 Kaggle 以及实验复盘。

---

## 二、任务分析

### 2.1 任务特点

该比赛任务具有以下特点：

1. **时间序列长度较长**  
   每个 `series_id` 对应一段较长的连续传感器记录，不能简单地将每一行数据看作独立样本。

2. **事件极其稀疏**  
   对于一整晚甚至多天的数据，`onset` 和 `wakeup` 事件只出现少数几次。大部分时间步都不是事件点。

3. **预测结果需要后处理**  
   模型通常会输出每个时间步属于 `onset` 或 `wakeup` 的概率，但 Kaggle 提交格式需要离散事件点，因此必须进行峰值检测、阈值筛选等后处理。

4. **本地验证与排行榜分数存在差异**  
   本地 OOF 分数和 Kaggle Public/Private 分数并不完全一致。这说明验证集划分、后处理策略和泛化能力都很重要。

---

## 三、整体方法

本项目采用的整体流程如下：

```text
原始数据
  ↓
特征工程
  ↓
构造软标签
  ↓
时间序列窗口切分
  ↓
深度学习模型训练
  ↓
输出每个 step 的事件概率
  ↓
后处理生成 onset / wakeup 事件点
  ↓
生成 submission.csv
  ↓
提交 Kaggle
```

整体思路是将事件检测问题转化为一个 **dense sequence prediction** 问题，即让模型对每一个时间步都输出事件概率。

---

## 四、数据处理与特征工程

### 4.1 输入数据

主要输入数据包括：

- `train_series.parquet`
- `train_events.csv`
- `test_series.parquet`

其中 `train_series.parquet` 存储传感器时间序列，`train_events.csv` 存储真实的 `onset` 和 `wakeup` 标签。

### 4.2 基础特征

模型使用的基础特征包括：

- `anglez`
- `enmo`
- `log1p_enmo`
- `d_anglez`
- `abs_d_anglez`
- `d_enmo`
- `abs_d_enmo`

其中差分特征可以帮助模型感知运动状态的变化。

### 4.3 滚动统计特征

为了让模型获得局部上下文信息，构造了多个窗口尺度的滚动统计特征，例如：

```text
anglez_mean_12
anglez_std_12
enmo_mean_12
enmo_std_12
anglez_mean_60
anglez_std_60
enmo_mean_60
enmo_std_60
...
```

这些特征帮助模型判断当前时刻附近的运动是否平稳。例如，入睡后通常运动强度降低，`enmo` 的均值和标准差可能变小。

### 4.4 时间特征

由于睡眠事件与一天中的时间有强相关性，因此加入周期性时间特征：

```text
hour_sin
hour_cos
minute_sin
minute_cos
weekday_sin
weekday_cos
```

使用 `sin/cos` 的原因是时间具有周期性。例如 23 点和 0 点在数值上差距很大，但实际时间上相邻。

---

## 五、标签设计

### 5.1 问题

原始事件标签是离散点，例如某个 step 是 `onset`。如果直接让模型只在单个点预测 1，其余点预测 0，会导致标签极其稀疏，模型很难学习。

### 5.2 软标签设计

因此，本项目将事件点扩展为高斯软标签。也就是说，距离真实事件越近的位置，标签值越高；距离越远，标签值越低。

例如，对于某个真实 `onset`：

```text
真实事件点附近：标签接近 1
稍远位置：标签逐渐降低
很远位置：标签接近 0
```

这样做的好处是：

1. 增强训练信号
2. 允许模型学习“事件附近的模式”
3. 与 Kaggle 评价指标中的时间容忍机制更加匹配

---

## 六、模型结构

本项目使用了一个一维时间序列模型，整体结构类似 U-Net，并结合了 Conformer 和 Mamba-like 模块。

### 6.1 模型输入

输入为一个窗口内的时间序列特征：

```text
shape = [batch_size, window_size, feature_dim]
```

### 6.2 模型输出

模型对每个时间步输出四个概率：

```text
p_onset
p_wakeup
p_sleep
p_invalid
```

其中最重要的是：

- `p_onset`
- `p_wakeup`

这两个概率会在后处理阶段被转化为最终提交的事件点。

### 6.3 U-Net 结构

模型采用 encoder-decoder 结构：

```text
输入特征
  ↓
卷积投影
  ↓
编码器下采样
  ↓
Conformer / Mamba-like block
  ↓
解码器上采样
  ↓
逐时间步输出概率
```

U-Net 结构适合时间序列事件检测，因为它既能保留局部细节，也能通过下采样获得更大范围的上下文信息。

---

## 七、训练策略

### 7.1 窗口切分

由于完整时间序列很长，不能直接整段输入模型，因此将每条 series 切分为固定长度窗口。

实验中使用过的窗口设置包括：

```yaml
window_size: 7200
stride: 7200
```

这意味着每个窗口覆盖一段连续时间序列，模型在窗口内进行 dense prediction。

### 7.2 Event-focused Sampling

由于事件点非常稀疏，如果随机采样窗口，很多窗口可能完全不包含 `onset` 或 `wakeup`，训练效率较低。

因此引入了 **event-focused sampling**：

```yaml
window_sampling: event_focused
event_window_fraction: 0.8
```

也就是说，训练时优先采样包含事件的窗口，让模型更多地看到入睡和醒来的关键片段。

这一步对分数提升非常重要。

### 7.3 Focal Loss

在后续优化中，引入了 focal loss，用于缓解事件稀疏和正负样本不平衡的问题。

普通 BCE loss 对大量简单负样本也会计算损失，而 focal loss 会降低简单样本的权重，让模型更关注难样本和稀疏事件。

实验配置如下：

```yaml
loss:
  event_weight: 1.5
  event_loss: focal
  focal_gamma: 1.5
  focal_alpha: 0.65
  sleep_weight: 0.35
  boundary_weight: 0.1
```

这一改动使本地 OOF 分数从约 `0.077` 提升到约 `0.081`，说明模型确实更关注事件检测。

## 八、后处理方法

模型输出的是每个 step 的概率，但 Kaggle 需要提交离散事件：

```text
series_id, step, event, score
```

因此需要后处理。

### 8.1 平滑

对概率序列进行滑动平均平滑：

```yaml
smooth_window_steps: 36
```

平滑可以减少概率曲线中的噪声，使峰值更稳定。

### 8.2 峰值检测

对 `p_onset` 和 `p_wakeup` 分别进行峰值检测：

```yaml
peak_distance_steps: 180
```

该参数限制两个候选事件之间的最小距离，避免模型在同一事件附近产生过多重复预测。

### 8.3 阈值筛选

通过阈值过滤低置信度预测：

```yaml
score_threshold: 0.0001
```

在本项目中，阈值设置较低，因为 Kaggle 评价指标对召回率比较敏感，适当保留更多候选事件有助于提高分数。

### 8.4 最大事件数限制

为了避免生成过多无效事件，设置每个 series/event 的最大候选数：

```yaml
max_events_per_series_event: 200
```

## 九、实验过程与结果

### 9.1 初始实验

最开始使用较小规模配置进行训练，模型可以正常生成 submission，但分数较低。

初始 small 实验的 Kaggle 分数大约为：

```text
Private Score: 0.411
Public Score: 0.363
```

说明模型已经学到了一些基本规律，但仍然有很大提升空间。

### 9.2 Medium Plus 实验

之后扩大模型和训练设置，使用 `medium_plus` 配置。

该版本提交后获得：

```text
Private Score: 0.605
Public Score: 0.534
```

这是本项目中最稳定、最好的单次提交之一。

### 9.3 Large 模型实验

尝试使用更大的模型，即 `large 2-fold`，但结果反而下降：

```text
Private Score: 0.552
Public Score: 0.484
```

这说明模型变大并不一定带来提升。在数据量有限、训练预算有限的情况下，大模型可能更容易过拟合，或者训练不充分。

### 9.4 三模型融合实验

尝试了 `medium plus 3 model ensemble`，结果为：

```text
Private Score: 0.597
Public Score: 0.517
```

相比最好的 `medium_plus` 并没有提升。这说明简单增加模型数量并不一定有效，模型之间需要有足够差异性，融合才可能带来收益。

### 9.5 Event Plus 实验

引入 focal loss 和 event-focused loss 权重后，本地 OOF 分数提升：

```text
OOF local score: 0.0813719010877715
```

提交后结果为：

```text
Private Score: 0.597
Public Score: 0.543
```

该结果很有意思：Public 分数高于原来的 `medium_plus`，但 Private 分数略低。这说明 event_plus 学到了不同的模式，但泛化表现并不完全稳定。

### 9.6 内存优化实验

尝试扩大训练数据覆盖时，Kaggle notebook 出现内存不足：

```text
Your notebook tried to allocate more memory than is available. It has restarted.
```

为了解决这个问题，尝试实现 lazy window dataset，即不在初始化时一次性构建所有窗口特征，而是在训练时按需构建。

但是第一次 lazy 实现中出现了一个重要问题：特征是在窗口内部计算的，而原始 eager 版本是在整条 series 上计算 rolling features 后再切窗口。这导致 rolling 特征语义发生变化，分数明显下降：

```text
OOF local score: 0.0559
```

后来修复为“按需对整条 series 计算特征，再切窗口”，保持了与原始训练逻辑一致。

这个实验虽然没有最终用于提交，但非常有价值，因为它说明：

1. 工程优化不能改变数据语义
2. rolling feature 对上下文非常敏感
3. 内存优化需要谨慎验证

## 十、实验结果汇总

| 实验名称 | Private Score | Public Score | 说明 |
|---|---:|---:|---|
| small first run | 0.411 | 0.363 | 初始可运行版本 |
| medium plus 2 fold | 0.605 | 0.534 | 最佳稳定版本 |
| large 2 fold | 0.552 | 0.484 | 大模型反而下降 |
| medium plus 3 model ensemble | 0.597 | 0.517 | 简单融合无明显提升 |
| event plus 2 fold focal loss | 0.597 | 0.543 | Public 提升，Private 略降 |

最终选择 `medium plus 2 fold` 作为最稳定结果：

```text
Private Score: 0.605
Public Score: 0.534
```

## 十一、问题与反思

### 11.1 本地分数与排行榜分数不完全一致

实验中发现，本地 OOF 分数提升并不一定带来 Kaggle Private 分数提升。例如 event_plus 的本地 OOF 分数更高，但 Private 分数略低。

可能原因包括：

1. 本地验证集划分与测试集分布不同
2. 训练子集较小，验证不够稳定
3. 后处理参数对 Public/Private 的影响不同
4. 模型可能对某些 series 类型更敏感

这说明机器学习比赛中不能只看单一指标，需要结合本地验证、Public score 和 Private score 综合判断。

### 11.2 大模型不一定更好

Large 模型的结果反而下降，说明：

1. 模型容量变大后可能更容易过拟合
2. 训练 epoch 不足时，大模型可能没有收敛
3. 数据覆盖不足时，大模型优势无法发挥
4. Kaggle 资源限制会影响训练策略

因此，在实际项目中，模型复杂度需要与数据量、训练时间、硬件资源匹配。

### 11.3 后处理非常重要

该任务不是简单输出分类概率即可，而是需要将概率曲线转化为事件点。

后处理中的参数，例如：

```text
smooth_window_steps
peak_distance_steps
score_threshold
max_events_per_series_event
```

都会显著影响最终分数。

这让我认识到，在时间序列事件检测任务中，模型只是系统的一部分，后处理同样重要。

### 11.4 工程问题也是 AI 项目的一部分

项目过程中遇到了许多工程问题：

1. Kaggle 提交时需要关闭 Internet
2. GitHub clone 适合调试，但最终提交需要保证 notebook 离线运行
3. 不同 GPU 环境可能存在 CUDA 兼容问题
4. 扩大数据量容易导致内存爆炸
5. lazy loading 虽然省内存，但可能改变特征计算逻辑

这些问题说明，AI 项目不仅是训练模型，还包括环境管理、资源控制、代码部署和实验复现。

## 十二、收获

通过本项目，我主要学到了以下内容。

### 12.1 时间序列任务的建模方法

我理解了如何将时间序列事件检测问题转化为逐时间步预测问题，并使用深度学习模型输出每个 step 的事件概率。

### 12.2 标签设计的重要性

相比直接使用离散标签，高斯软标签更适合事件检测任务。它可以提供更平滑、更丰富的训练信号。

### 12.3 类别不平衡处理

由于 `onset/wakeup` 是稀疏事件，普通 BCE loss 容易被大量负样本主导。引入 focal loss 后，模型能更关注难样本和正样本附近区域。

### 12.4 调参不是盲目试

调参需要有明确目的。例如：

- 调 `event_weight` 是为了增强事件学习
- 调 `peak_distance_steps` 是为了控制重复预测
- 调 `score_threshold` 是为了平衡召回和误报
- 调 `window_size` 是为了改变上下文范围
- 调 `n_series` 是为了扩大训练覆盖

这些实验让我理解了参数背后的实际含义。

### 12.5 失败实验同样有价值

并不是所有尝试都会提升分数。例如 large 模型、三模型融合、pair filter、lazy window 初版都没有带来提升。但这些失败帮助我理解了模型容量、泛化能力、后处理和工程实现之间的关系。

## 十三、未来改进方向

如果继续优化，可以从以下方向入手：

1. **使用更多训练数据**  
   当前实验受限于 Kaggle 内存和时间，只使用了部分 series。未来可以优化数据加载，使模型训练覆盖更多样本。

2. **更稳定的交叉验证**  
   当前主要使用 2-fold。未来可以使用更多 folds，提高本地验证可靠性。

3. **改进模型结构**  
   可以尝试更成熟的时间序列模型，例如 TCN、Transformer Encoder、GRU 或 ConvNeXt-style 1D 网络。

4. **更系统的后处理搜索**  
   使用网格搜索或贝叶斯优化寻找更好的 `smooth_window_steps`、`peak_distance_steps` 和阈值。

5. **模型融合**  
   融合不同 loss、不同 seed、不同窗口长度的模型，而不是简单融合相似模型。

6. **优化内存与训练速度**  
   实现更合理的 lazy loading 或预处理缓存，在不改变特征语义的前提下降低内存占用。

## 十四、总结

本项目完成了一个较完整的 AI 时间序列事件检测系统。从原始 Kaggle 数据出发，经过特征工程、标签设计、模型训练、后处理调参和 Kaggle 提交，最终获得了较好的比赛成绩：

```text
Best Private Score: 0.605
Best Public Score: 0.534
```

虽然没有继续追求排行榜极限分数，但本项目的价值在于完整经历了机器学习项目的关键环节。通过多轮实验，我不仅理解了深度学习模型如何处理时间序列数据，也认识到特征设计、损失函数、采样策略、后处理和工程实现都会对最终结果产生重要影响。

本项目让我认识到，AI 实践并不是简单地训练一个模型，而是一个不断假设、实验、验证和反思的过程。最终分数固然重要，但更重要的是理解每一次改动为什么可能有效，以及为什么有些改动失败。对于 AI 导论课程而言，这次项目很好地帮助我将课堂中学习到的模型、损失函数、训练策略和实验评估方法应用到了真实任务中。
